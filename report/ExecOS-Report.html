01 · Executive summary

Project at a glance

ExecOS is an operating-systems learning workbench. Students sign in, explore OS algorithms through step-by-step interactive visualizations, read a full concept lesson, take a 20-question quiz per topic, and practise on scenario challenges. Alongside the learning side, a live, deterministic Kernel Engine simulates a full operating system (processes, scheduling, memory, files, devices, IPC, resources, interrupts and system calls) that users can operate and inspect. ExecAI sits on top as a read-only assistant that explains, diagnoses and recommends.

Three distinct cores

ExecOS Workbench (React)

The browser application: sign-in, Learning Hub, simulator labs, Challenge Mode, Engine management and inspection pages, ExecAI console and settings.

Kernel Engine (Python / FastAPI)

A deterministic, in-memory software OS. It owns the process table, scheduler, memory, files, devices, IPC, resources, interrupts, syscalls and the execution trace. Restarting the backend resets it.

ExecAI (observability layer)

Reads Engine snapshots and trace records to explain, analyze, recommend and teach. It never changes live state without explicit user approval. Optional local LLM chat through Ollama.

x86-64 kernel (C)

A real freestanding kernel booted by Limine under QEMU, with a frame allocator, heap, interrupts, preemptive kernel threads, a RAM filesystem, tracing and a serial shell. Built and run separately.

Who it is for

  • Students learning operating systems: visual, step-by-step understanding plus self-testing.
  • Instructors: a ready-made lab for demonstrating scheduling, memory, deadlock and file-system behaviour live.
  • Systems learners: a bridge from simulated concepts to a real, bootable kernel.

03 · Accounts & sign-in

Welcome screen

  • Sign up with full name, email and password (at least 10 characters, confirmed). A username is derived from the email automatically.
  • Log in with email and password; "Remember me" keeps the session in local storage, otherwise it lasts for the browser session.
  • Passwords are stored as salted PBKDF2-SHA256 hashes in SQLite and compared in constant time. Sessions are bearer tokens, and every Engine, ExecAI and learning endpoint requires one.
  • A session is an application login only. It is not an OS user and grants no host privileges.
  • The Google and GitHub buttons are present in the UI as placeholders.
04 · Learn

Overview dashboard

The home page after sign-in. A persistent layout frames every page: a top bar with live host stats (architecture, CPU, memory, process count, uptime) and the Engine status, a grouped side navigation (Learn, Manage, Inspect, Tools), and a status bar.

  • Module launcher: 12 cards, each with the algorithms it covers, that open straight into the Simulator.
  • Engine summary: processes (ready/waiting), Engine memory used/free, last CPU run, and I/O queue depth.
  • Run the Engine scheduler from the dashboard (policy + time quantum), with the process-state table and a Gantt timeline.
  • Host details (read-only) and the recent Engine events feed.

09 · Tools

ExecAI & Settings

ExecAI is an observability layer, not a control plane. It reads Engine snapshots and trace records; diagnoses show their measured evidence; the optimizer and What-If Lab run real schedulers on isolated copies. Live state changes only when the user explicitly confirms a recommendation.

9.1 ExecAI · Live Engine

  • Modes: OS Expert, Debug, Learning and General technical reference, with a session activity log.
  • Diagnose ExecOS: deterministic rules over a fresh snapshot and trace, such as READY-queue and process-state mismatches, with a health score that discloses its coverage.
  • Self-healing Recovery Manager: Detect → Analyze → Diagnose → Recommend → Approve → Recover → Verify. It rejects stale plans and verifies queue and CPU-owner consistency after execution.
  • Optimizer and What-If Lab: compare scheduling policies on isolated Engine copies. Trend predictions use retained history and say when there is not enough of it.

11 · The x86-64 kernel

Freestanding kernel under QEMU

A separate, real kernel written in freestanding C and x86-64 assembly, booted by Limine and run in QEMU. A prebuilt execos.iso is included in the project.

Limine → freestanding x86-64 kernel
       → physical-frame allocator (pmm.c) and page-backed kernel heap (heap.c)
       → IDT, legacy PIC/PIT interrupts (idt.c, pic.c, interrupts.S)
       → preemptive round-robin kernel threads (scheduler.c, process.c)
       → bounded RAM filesystem (filesystem.c) and trace ring (trace.c)
       → COM1 serial shell (shell.c, serial.c)

Serial shell commands

helpclearpwdcdlsmkdirtouchcatwritermmvpskillmemoryschedulertraceuname

Build & test (Ubuntu on WSL2)

sudo apt install build-essential git curl xorriso qemu-system-x86
make            # build kernel + ISO
make run        # boot in QEMU
make test-memory  test-heap  test-process  test-filesystem  test-shell  test-trace  test-boot
Current limits: ring-0 worker threads in one shared address space. There is no ring-3 user mode, no isolated per-process address spaces, no userspace syscall ABI, no persistent filesystem, and no telemetry bridge to the GUI.

Security and design safeguards

  • Salted PBKDF2-SHA256 password hashing with constant-time comparison; bearer-token sessions on all protected routes.
  • The API binds to loopback by default, and CORS is configurable through EXECOS_CORS_ORIGINS.
  • The Ollama endpoint is restricted to localhost; the assistant cannot browse the web or control the host.
  • Host telemetry is strictly read-only and never substituted for Engine state.
  • AI analysis never mutates live state; recovery requires a plan ID plus explicit approval, rejects stale plans and verifies the result.
  • Pydantic validation on every request body, with bounded values such as quantum ≤ 10,000 and memory ≤ 4,096 MB.

14 · Scope, boundaries & known limits

What ExecOS is and isn't

It is

  • A complete OS learning path: visualize, learn, quiz, challenge.
  • A deterministic software OS engine you can operate and trace.
  • An evidence-based assistant that explains rather than guesses.
  • A real bootable kernel project for going deeper.

It isn't

  • A live QEMU guest. The Engine and the kernel are deliberately separate.
  • Persistent: Engine state resets when the backend restarts (accounts and progress persist).
  • A host controller: host data is read-only.
  • Fully featured in "conceptual" labs: fork, exec, wait and exit are labelled as concept-only.

Known limits observed while preparing this report

  • Local AI chat needs Ollama with the configured model installed; otherwise it reports the missing model (Fig 31).
  • The Google and GitHub sign-in buttons are UI placeholders.
  • The Engine supports FCFS, SJF, SRTF, Priority and Round Robin. Non-preemptive Priority exists only in the educational lab.
  • The kernel has no user mode or GUI bridge yet (see section 11).
